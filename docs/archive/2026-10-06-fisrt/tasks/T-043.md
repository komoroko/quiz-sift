## Acceptance criteria

> 機械可読な写しは `.rein/plan.yaml` のこのタスクの `acceptance:` にあり、ループが読むのはそちら。

- **A-1**: ClaudeCliLlm が組み立てる argv は、次のものを含む: 有効ツールを StructuredOutput に絞る --settings の deny 列挙、--strict-mcp-config と空の --mcp-config、--output-format stream-json と --verbose、3 以上の --max-turns、--safe-mode。--dangerously-skip-permissions は含まず、--permission-mode は bypassPermissions / acceptEdits でない。システムプロンプトにも argv のどこにも教材本文が入らない。T-041 の success と success_opus の meta が記録した argv と、プロンプト・スキーマ・モデル以外で一致する。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_argv_matches_the_frozen_shape_and_the_fixture`
- **A-2**: ClaudeCliLlm.__init__ の本体は、属性代入と引数なしのクラス呼び出しだけである。if / match / try / 添字 / os.environ / ファイル読み出し / importlib を含まず、キーワード既定値を持たない(AST で判定する)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_init_body_is_assignments_and_bare_class_calls`
- **A-3**: Workspace を tmp_path を根にした実物のまま使い、spawn だけを fake に差し替えて呼び出す。このとき、製品が HOME 配下に作成したファイルは 0 件で、runner が観測した env のキーは {HOME, PATH, LANG, TZ} と一致する。CommandSpec.cwd はその呼び出しの new_cwd() であり、spawn の時点で空である。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_a_call_creates_nothing_under_home`
- **A-4**: usage は成否の判定より先に meter へ渡る。PARSE / SCHEMA / TRUNCATED / INCOMPLETE_IDS / PROVIDER_ERROR のどれで終わった呼び出しでも、トークンが記録される。1回の classify_clusters は 25 問ごとに分割されて provider_invocations を増やし、llm_calls は 1 だけ増える。失敗は ClassificationResult.failures に入り、その reason は FailureKind の値で始まる。再試行はしない。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_usage_is_recorded_before_judging_and_no_retry`
- **A-5**: 実パーサが、T-041 の実物フィクスチャ3件を、meta の exit_code と stderr を付けたまま判定器へ渡して読む。success と success_opus は割当を返し、invalid_schema は PARSE に落ちる。これとは別に、tests/support/claude_fake.py のファクトリが error_max_turns 形を作る。成功フィクスチャの骨格から subtype / is_error / stop_reason / structured_output の値だけを置き換え、キーは消さない。この形は TRUNCATED に落ち、その骨格は差し替えた4キー以外で成功フィクスチャと同一である(D-118)。  
  判定: `pytest -q tests/adapters/test_claude_contract.py::test_real_fixtures_parse_to_the_expected_kinds`
- **A-6**: fake の出力は、tests/support/claude_fake.py の単一のファクトリだけが作る。判定には T-042 の assert_no_inline_stream_json(tests_root) を使う。result イベントを持つすべての形(成功、TRUNCATED、PROVIDER_ERROR、SCHEMA、INCOMPLETE_IDS、overage、rejected)の出力は、キー骨格が成功フィクスチャと同一である。result を持たない PARSE 形は対象外。usage.cache_read_input_tokens を落とした fake に対して、この骨格判定は赤になる(negative control)。ファクトリは、PATH に置ける実行ファイルとしての入口も提供する。この入口は stdin のプロンプトから問題キーを読み、同じ多重集合を返す。  
  判定: `pytest -q tests/adapters/test_claude_contract.py::test_fake_output_has_the_fixture_skeleton_with_negative_control`
- **A-7**: fake による1回の呼び出しで、記録用の meter に次の値が実際に届く: begin_invocation の現 argv のダイジェスト、end_invocation の model・num_turns・usage・total_cost_usd・result の is_error・skills_digest(init.skills から overhead.skills_digest で計算した値)、その子の rate_limit_event ごとの record_quota(順序どおり)。どれか1つを渡さない実装は赤になる。実物の success と success_opus を返す呼び出しで meter が受け取る model は、pipeline/meter.py の単価表のキー(claude-haiku-4-5 / claude-opus-5-5)と一致する(assistant イベントの日付付き ID を渡さない。AR-143)。argv のダイジェストはプロンプトとスキーマの本文を除いた argv から取る: プロンプトとスキーマだけが違う2つの呼び出し(classify と summarize)のダイジェストが等しく、モデルだけが違えば異なる(D-107、AR-144)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_every_nfr7_value_reaches_the_meter`
- **A-8**: check_entailment は llm_contract の判定語パーサを通る。未知の判定語は CONSISTENT にならない。check_entailment の呼び出しが PARSE / SCHEMA / TIMEOUT / PROVIDER_ERROR / TRUNCATED のどれで失敗しても、CONSISTENT は返らず、safety.entailment.emit_if_consistent は成果物を書かない(fail-closed。C-013、AR-147)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_entailment_uses_the_shared_parser`
- **A-9**: (h) を実 Meter を通して判定する。実物の success フィクスチャを返す呼び出しでは overage_check が passed になる。ファクトリで isUsingOverage を真にした形では、その呼び出しが PROVIDER_ERROR の失敗になり、overage_check が failed になる。rate_limit_event を落とした形では unknown になる。これは unknown を passed に潰す実装を赤にする negative control である(D-125、D-140)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_overage_check_passes_on_the_real_fixture_and_fails_on_overage`
- **A-10**: classify_clusters の中の早期停止(D-144)。60 問(3バッチ)の分類で、1バッチ目の子に isUsingOverage 真が現れたら、残り2バッチは spawn されない(spawn 回数 1)。1バッチ目が status: rejected かつ is_error 真で失敗した場合も同じ。失敗件数は、実際に発行した呼び出しについてだけ数える。1バッチ目が SCHEMA で失敗した場合は、3バッチとも spawn される。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_overage_or_rejected_stops_the_remaining_batches`
- **A-11**: fake による1回の呼び出しごとに、T-042 の InvocationRecord が1件、ログへ出る。合成の教材本文を含む stdout はマスクされ、stdin の本文(プロンプト)はログのどこにも現れない(sha256 と長さだけ)。stdout や stderr を InvocationRecord を経ずに書く経路は無い(C-014、C-015、AR-146)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_each_invocation_emits_one_masked_record`
- **A-12**: runner の実行中に SystemExit の派生が送出されたら、ClaudeCliLlm はそれを失敗(SPAWN など)に変えず、そのまま再送出する。meter の failures_by_kind は増えない(AR-149)。  
  判定: `pytest -q tests/adapters/test_llm_claude_cli.py::test_system_exit_passes_through_uncounted`
