# ADR-018: フル処理を run_id の実行の列として数え、レート枠による停止と overage を呼び出し単位で判定する

- **Status**: accepted
- **Date**: 2026-09-26
- **Decider**: human (finalized at the mandate)
- **Related requirements**: R-3, NFR-7, NFR-8 (f)(h)
- **Decisions**: D-123, D-124, D-125, D-128, D-129, D-132(このほかに loop が決めたもの: D-134〜D-140、D-142〜D-145)

## Background / problem

D-091 の撤回で、レート制限は `PROVIDER_ERROR` として失敗に数えることになった。人は枠のリセット後に再実行する。

困るのは、週次枠が 95% の状態で 100〜200 問のフル処理を実測する場合(T-020)である。
- 1つの枠の中で完走するとは限らない。
- 再実行した実測を「フル処理1回」と数える定義が無かった。
- `isUsingOverage`(サブスクリプションの超過分の従量課金)を誰も見ていなかった。

## Options

### Option A: 1回の実行だけをフル処理と数える
- 再開した実測は数えない。
- 枠が binding なら、T-020 は永遠に完走しない。

### Option B: 同じ run_id で連なる実行の列を1回と数え、合算する(採用)
- 初回は段キャッシュを迂回し、再開は段キャッシュから読む。
- 途中の実行が止まってよいのは、レート枠による停止のときだけ。
- 完走は、最後の実行が exit 0 で終わること。

### Option C: 段の中で呼び出し単位に再開する
- 却下(D-129)。作るには、呼び出し単位の成果物キャッシュが要る。1つの段は1つの枠に収まる、という前提を要件に書いた。

## Decision

**Adopted**: Option B。

判定の定義は次のとおり。

- **レート枠による停止**(D-128、D-135)は、呼び出しごとに判定する。その実行で失敗した呼び出しの**すべて**が、次の4条件を満たすこと。
  1. 失敗種別が `PROVIDER_ERROR` である。
  2. `result.is_error` が真である。
  3. **自分の子プロセス**が最後に出した `rate_limit_event` の `status` が `rejected` である。
  4. 同じイベントの `isUsingOverage` が偽である。

  並行時に、他の呼び出しのイベントを借りることはできない。
- **overage**(D-125)
  - `isUsingOverage` が真の呼び出しは `PROVIDER_ERROR` として数え、非 0 終了する。
  - 列全体で真が 1 件でもあれば、その列は完走不可になる。
  - `rate_limit_event` が届かなかった呼び出しが 1 件以上あれば、(h) は `unknown` と報告する。
- **`resetsAt`**(D-123)は、`rate_limit_event` が届いていた場合に限って残す。
- **列への登録**(D-132)
  - 起動前検査を通った起動だけを、実行として列に登録する。
  - 登録は、最初の LLM 呼び出しより前に行う。
  - 終了の記録が無い登録は、レート枠以外の停止として数える。

**Reason**: 1回の実行でしか数えないと、枠が binding な状況で実測そのものが成立しない。そのうえで、停止を許す範囲は、実行ファイルのスキーマから読める最も狭い形に絞った。枠切れの実物は、まだ観測できていない。

## Consequences / results

- `run_id` の意味が「列の ID」に変わる。1回の実行は `execution_id` で識別する。
- 列の操作:
  - 始める: `--fresh-run`
  - 足す: `--resume RUN_ID`
  - 無指定: 通常のキャッシュを使う、1実行だけの列になる(D-136)。
- 迂回は、`--fresh-run` / `--resume` の実行の `inputs_digest` に `run_id` を加えて列ごとに成果物を分けることで行う(D-137)。
- `--resume` は `resumable` の列にだけ許す。`completed` は最後の実行が最終段 `audio` を exit 0 で終えた列に限る(D-145)。
- overage か `rejected` を観測したら、その段の残りの呼び出しは発行しない(D-144)。
- 上限と集約:
  - 12 時間の上限は、1回の実行ごとに `signal.alarm` で掛ける(D-138)。
  - 列の集約は、各実行の終了行に書く(D-139)。
- 段の途中で止まった段は、再開時に最初から呼び直す。そのため、列の合算の `llm_calls` は、止まらずに走った1回分より多くなる。要件は「和」を課しているので、重複は除かない。
- 枠切れのとき CLI が何を出すかは、未観測のまま残る。
  - 出力が `rejected` の `rate_limit_event` を伴わない形なら、枠切れの停止はすべて列を完走不可にする。
  - その場合、T-020 は複数の枠にまたがって完走できない。そうなれば次サイクルで扱う(D-129)。
- `ports/metering.py` の `ALLOWED_STATUS` と、D-110 の判定(`status != "allowed_warning"` なら真)は削除する。
  - 成功フィクスチャには `status: allowed` が出ており、この判定では誤ってレート制限に数える。

### What this requires of a person

- 枠のリセット後に `--resume <run_id>` で再開すること。`resetsAt` はログで読む。
- 列の `status`(`completed` / `resumable` / `not_completable`)と `not_completable_reasons` を読むこと。
- (h) が `unknown` のとき、課金画面を目視するかどうかを判断すること。
- 段が1つの枠に収まらず、列が完走しないときは、次サイクルへ回すかどうかを判断すること。

### Reversibility

- コードは**可逆**(revert で戻る)。
- 列のログは `out/<deck>/meter.jsonl`(gitignored、追記のみ)にあり、消せば戻る。
- T-020 の実行そのものは、D-088 の不可逆ゲートに残る。この ADR は不可逆な点を増やさない。
