## Acceptance criteria

> 機械可読な写しは `.rein/plan.yaml` のこのタスクの `acceptance:` にあり、ループが読むのはそちら。

- **A-1**: --fresh-run を付けた LLM 段は、新しい run_id を採番して stderr に表示する。開始行(cache_mode: fresh)は、最初の spawn より前に fsync まで済んでいる。fake runner が spawn の時点でファイルを読んで確かめる。同じ入力の通常の実行が作った成果物があっても、段キャッシュにヒットせず spawn する。fresh / resume の実行の inputs_digest には run_id が入る。通常の実行(cache_mode: normal)の digest は変わらない(既存の tests/pipeline/test_stage.py のノードが緑のまま)(D-136、D-137)。  
  判定: `pytest -q tests/test_cli_sequence.py::test_fresh_run_registers_and_bypasses_the_cache tests/pipeline/test_stage.py`
- **A-2**: --resume RUN_ID が許されるのは、列の status が resumable のときだけである。存在しない run_id・completed・not_completable の列では、即座に非 0 終了し、開始行を書かず、spawn も 0 回になる。resumable の列で再開すると、その列が作った段はキャッシュから読まれ(spawn 0 回)、ほかの列や通常の実行が作った成果物にはヒットしない(D-145)。  
  判定: `pytest -q tests/test_cli_sequence.py::test_resume_is_allowed_only_for_a_resumable_sequence`
- **A-3**: LLM 段(cluster / recall / glossary / script / audio)は、開始行を書く前に preflight を呼ぶ。preflight が落ちると、非 0 終了し、meter.jsonl に1行も足さず、spawn も 0 回になる(D-132)。ingest / review / serve は preflight を呼ばない(D-143)。inspect.signature(cli.main) の llm_factory と preflight の既定値は、composition.build_default_llm と claude_process.default_preflight そのものである。入口のすべてが main を argv だけで呼ぶことを、AST で判定する。  
  判定: `pytest -q tests/test_cli_sequence.py::test_preflight_runs_before_registration_on_llm_stages_only tests/nfr8/test_entry_points.py::test_entry_points_call_main_with_argv_only`
- **A-4**: 1回の実行の上限は signal.alarm で掛かる。上限定数を1秒に差し替え、rate_limit_event を1件出したあと止まらない fake を与えると、非 0 終了になり、子プロセスは kill され、終了行が書かれる(stop.kind: other、exit_reason は SystemExit の派生クラス名)。その終了行の quota_at_end に、そのイベントの resetsAt が残る(C-003、D-138、AR-150)。  
  判定: `pytest -q tests/test_cli_sequence.py::test_the_execution_limit_stops_with_an_end_line`
- **A-5**: 終了行は finally で書かれる。exit 0、失敗による非 0、上限による停止のいずれでも、開始行と終了行が1組ずつ残る。キャッシュだけで終わる実行(spawn 0 回)も2行を書く(Meter は開始行の時点で作る)。  
  判定: `pytest -q tests/test_cli_sequence.py::test_every_execution_writes_both_lines`
- **A-6**: 段をまたぐ早期停止(D-144)。3クラスタの recall 段で、1つ目の呼び出しの子に isUsingOverage 真が現れたら、残り2つは spawn されない(spawn 回数 1)。実行は非 0 終了し、サマリの失敗件数は 1 になる。1つ目が status: rejected かつ is_error 真で失敗した場合も同じ。1つ目が SCHEMA で失敗した場合は、3つとも spawn される。  
  判定: `pytest -q tests/test_cli_sequence.py::test_overage_or_rejected_stops_the_rest_of_the_stage`
- **A-7**: fake による端から端までの列を2通り走らせる。1つ目: fresh の cluster(exit 0)→ recall が rejected で停止 → resume で audio まで exit 0。最後の終了行の sequence.status は completed で、合算の llm_calls は各実行の和である。2つ目: 同じ流れで recall に overage を出す。列は not_completable になり、その後の --resume は拒否される。TTS は StubTts を使う。absorb タスクの受入テストは緑のまま残る。  
  判定: `pytest -q tests/test_cli_sequence.py::test_a_sequence_completes_across_a_rate_limit_stop_and_overage_does_not tests/acceptance/`
- **A-8**: 開始行の env_names の集合は、テストが与えた親環境の変数名の集合とちょうど一致し、値を含まない(AR-158)。metered_env_names は、その一覧と NFR-8 が列挙した13変数(テスト側に要件から写したリテラル)の積集合である。13変数を1つずつ親環境に入れて走らせると、それぞれの metered_env_names がその1変数だけになり、列の status は not_completable になる。何も入れなければ空になる(C-020、AR-137)。  
  判定: `pytest -q tests/test_cli_sequence.py::test_metered_env_names_come_from_the_parent_environment`
