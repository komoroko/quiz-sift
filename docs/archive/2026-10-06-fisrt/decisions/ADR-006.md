# ADR-006: 判定されるロジックは全部 Python 側、UI は表示と OptionId 送信のみ

- **Status**: accepted
- **Date**: 2026-09-22
- **Decider**: human (finalized at the mandate)
- **Related requirements**: R-8, R-12

## Background / problem

R-8 の受入基準に「既知フィクスチャに対し、シャッフル提示下で全問正解入力が正答率 100%、
全問誤答入力が 0%」がある(AR-4 が塞いだ穴)。この判定をどちらの言語に置くかで、証拠能力が変わる。
品質ゲートにも CI にも node は無い(ADR-012 で入れるが、それは E2E のため)。

## Options

### Option A: Python が HTTP API、UI は表示と `OptionId` 送信のみ
- Overview: `http.server`(stdlib)でローカル API。Next.js は `presentation` を表示して `OptionId` を送る。
- Non-functional: **採点・シャッフル・レポートが全部 Python 側に残るので、R-8 の全受入基準が
  `command` で機械判定できる**。
- Implementation effort: 中(手書きのルーティング)。起動は2プロセス。

### Option B: FastAPI + uvicorn
- Pros / cons: スキーマ検証と OpenAPI が付くが依存が増える。ADR-001 の方針とは矛盾しない。

### Option C: Next.js が直接 DB を読み書き
- Pros / cons: **書き込みロジックが2言語に分裂し、採点が node 側に漏れると AR-4 が塞いだ穴の検証が
  ゲートから消える**。

### Option D: Next.js を静的エクスポートして Python が配信
- Pros / cons: 起動が1コマンドになるが、Server Component / SSR が使えない。

## Decision

**Adopted**: Option A

**Reason**: 受入基準の証拠能力が最大になる。判定されるロジックを、判定できる場所に置く。

## Consequences / results

- **回答の受け口は `submit(question_id, chosen: OptionId)` のみ**。表示位置インデックスを受け取る
  API を存在させない。これで AR-4 の裏切り実装は「書けるコード上の経路が無い」状態になる。
- UI に `localStorage` への永続化経路を作らない。
- `web/` から LLM SDK を import しないことをレビューで見る。
- 起動は2プロセス(`quiz-sift serve` と Next.js)。
- **What this requires of a person**: ポート番号の選択。2プロセスを起動すること。
- **Reversibility**: 可逆。`server/` の差し替えで済む。
