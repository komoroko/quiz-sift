## Acceptance criteria

> 機械可読な写しは `.rein/plan.yaml` のこのタスクの `acceptance:` にあり、ループが読むのはそちら。
> **受入基準1本につきテストのノード ID を1つ割り当ててある**(タスクレビュー AR-1)。

- **A-1**: 排他分割が強制され、分類できない問題が「その他」クラスタへ入り、全問題 ID の一覧が各クラスタに付く。クラスタ数 M と M/N が記録される。  
  判定: `pytest -q tests/cluster/test_assign.py::test_exclusive_partition_and_metrics`
- **A-2**: 既知5グループ(各3問以上)の固定フィクスチャに対し、最大クラスタが全体の 50% 以下かつ「その他」比率が 20% 以下になる。  
  判定: `pytest -q tests/cluster/test_degeneracy.py::test_known_five_groups_pass_the_guard`
- **A-3**: 退化スタブ2本(全問1グループ / 全問未分類)に対して、上のガードが赤くなる。  
  判定: `pytest -q tests/cluster/test_degeneracy.py::test_degenerate_stubs_go_red`
- **A-4**: 外部 API 呼び出しに失敗があった実行は下流へ進まず非0終了し、サマリに other_ratio / max_cluster_ratio / failure_count が実際の値と一致して出る。  
  判定: `pytest -q tests/cluster/test_failures.py::test_partial_failure_stops_the_pipeline`
- **A-5**: 要約の主要語句が当該クラスタの問題文に実在することが grounding 越しに判定される。実在しない語を含む要約は赤になる。  
  判定: `pytest -q tests/cluster/test_summary.py::test_summary_terms_must_exist_in_the_cluster`
- **A-6**: 仕込んだ矛盾を持つクラスタ要約フィクスチャに対し、含意判定が呼ばれて成果物を書かずに非0終了する。entailment を一度も呼ばない実装は赤になる。  
  判定: `pytest -q tests/cluster/test_summary.py::test_summary_goes_through_entailment`

## Automated-test approach (the basis for the green decision)

- **Test kind**: unit / integration
- **Test file(s)**: `tests/cluster/test_assign.py`, `tests/cluster/test_degeneracy.py`, `tests/cluster/test_failures.py`, `tests/cluster/test_summary.py`
- **Test target / cases** — 各ノードについて **何を壊すと赤になるか**:

  - **A-1**: 多重所属を許す / M や M/N を記録しない実装 → 赤
  - **A-2**: 既知5グループを1つにまとめる実装 → 赤
  - **A-3**: ガードが常に True を返す実装 → 退化スタブで赤にならないので、このノード自体が赤
  - **A-4**: failures を握りつぶして下流へ進む / failure_count を実数と違う値で報告する実装 → 赤
  - **A-5**: 要約の語句実在性を判定しない実装 → 実在しない語を含む要約フィクスチャで赤
  - **A-6**: cluster/summary.py が entailment を import しない実装 → 仕込んだ矛盾で 0 終了するため赤

> ノード ID は「その名前のテストが存在すること」までしか強制しない — **空の本体(`pass`)でも exit 0 になる**
> ことは実測で確かめてある。上の行は、実装者とレビュアーがその空白を見つけるための唯一の非循環な手掛かりで、
> 最終的な防御はタスク DoD の `review` ステップ(コードレビュアーがテストを読む)。
