# Requirements

> `/req` generates/updates this, sounding out from `docs/00-product-brief.md`.
> Finalized once a human approves at **the mandate**. Changes after approval need re-approval.

## Summary

4択問題集を AI が分析し、背後にある知識・出題パターン・紛らわしい選択肢の違いへ圧縮したうえで音声化する。
机に向かえない時間を復習に使えるようにし、学習の前後で正答率を測定して記録する。
問題の取り込みから音声の書き出しまでを Python CLI が担い、テスト出題と学習記録は Web UI が担う。

## 優先度と acceptance の関係

Priority(Must / Should / Could)は **実装の着手順序** を表し、未達を許す指定ではない。
`.rein/plan.yaml` に凍結された 18 本の claim はすべて acceptance の判定対象であり、
未達の claim が1本でもあれば acceptance は通らない。範囲を削る場合は mandate の承認前に
要件ごと落とす(`/revise` ではなく承認前の縮小)。R-9(音声回答と AI 採点)はこの経路で
承認前に落とした要件であり、**R-9 は欠番**である。採番を詰めないのは、決定の履歴を
追えるようにするため。

## List of things to achieve

### R-1: 問題データの取り込みと正規化
- **Overview**: 4択問題(問題文・選択肢4件・正解・既習フラグ・あれば公式解説)の集合を構造化ファイルから読み込み、内部形式へ正規化する。
- **Background / why needed**: 以降のすべての工程の入力。ここで欠損を素通りさせると、圧縮も測定も静かに壊れる。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 100〜200問を読み込み、取り込めた問題すべてについて問題文・選択肢4件・正解1件が欠落なく保持される
  - [ ] 選択肢数が4でない、正解が特定できない、ID が重複する問題は取り込み時に個別に列挙され、除外件数が報告される
  - [ ] 取り込み件数 + 除外件数 = 入力件数 が常に成立する
  - [ ] **正常系フィクスチャ(全問が妥当な形式)に対して、除外件数が 0 になる**(パーサが厳しすぎて大半を捨てても保存則だけは成立してしまうため)
  - [ ] 文面がほぼ同一の重複問題が検出され、件数が報告される
  - [ ] **入力形式が既習フラグの列を持ち、その値(`studied` / `unseen`)が取り込み時に読み取られる**。個別の指定が無い問題にはセット単位の指定(R-11)が適用され、**個別指定もセット指定も無い場合に限り** `unknown` として記録される。`unknown` を `studied` / `unseen` のどちらかで埋めることはしない
  - [ ] **公式解説を持つ問題の件数と持たない問題の件数が報告される**(NFR-1 の照合先がどれだけあるかを承認前に知るため)

### R-2: Udemy からの問題自動抽出
- **Overview**: Udemy の問題集ページからヘッドレスブラウザのスクリプトで問題文・選択肢・正解・解説を抽出し、R-1 の入力形式で書き出す。
- **Background / why needed**: 教材を手作業で起こす手間が続くと、100〜200問規模の運用が成立しない。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 1模試分のページから、抽出できた問題数と抽出できなかった問題数の両方が報告される
  - [ ] 抽出結果が R-1 の入力形式として妥当であることが、書き出し時に検証される
  - [ ] ページ構造の変化などで抽出できなかった箇所は、黙って空文字で埋めずエラーとして列挙される
  - [ ] **人手で正解を確認した10件のゴールデンセットに対し、抽出した正解ラベルの一致率が 100% である。この10件は、受験者の選択と正解が異なる問題を3件以上含む**(正答した問題だけで構成すると、自分の選択を正解として拾う実装がそのまま 100% になる)
  - [ ] **正解と判定した根拠の要素種別が記録され、全問で同一種別である**(ゴールデンセットの10件だけを特別扱いする実装を弾く)
  - [ ] **各問題について、どの要素を根拠に正解と判定したかが記録され、目視で追跡できる**(結果ページは自分が選んだ選択肢と正解の両方を強調するため、取り違えると誤った正解ラベルが取り込まれ、NFR-1 がそれを正しい生成物のエラーとして扱う向きに働く)
  - [ ] **公式解説を取得できた問題数と、できなかった問題数が報告される**
  - [ ] 抽出した問題文が、`.gitignore` の対象であることを起動時に検証したパスにのみ書き出される(NFR-2 と対)

### R-3: 類似問題のクラスタリング(圧縮)
- **Overview**: 問題群を、背後にある知識・出題パターンごとの排他クラスタへまとめる。
- **Background / why needed**: 「100問を100個の知識として覚えない」というプロダクトの中心にある考え方の実体。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] N 問の入力に対しクラスタ数 M が出力され、M / N が記録される
  - [ ] すべての問題がちょうど1つのクラスタに属する(排他分割)。分類できない問題は「その他」クラスタとして明示され、その比率が記録される
  - [ ] **退化ガードの判定に用いる固定フィクスチャが、既知の 5 グループから成り、各グループが3問以上を持つものとして定義されている**(フィクスチャの構成が未定義だと、正解となるグループ構造が無いため下の基準は何とでも満たせる)
  - [ ] **そのフィクスチャに対し、最大クラスタに属する問題数が全体の 50% を超えない**
  - [ ] **そのフィクスチャに対し、「その他」クラスタの比率が 20% 以下である**
  - [ ] 実データに対する最大クラスタ比率と「その他」比率が記録される(合格ラインは設けない)
  - [ ] 各クラスタに、属する全問題 ID の一覧が付随する
  - [ ] **キャッシュを迂回して再クラスタリングした2回の実行について、問題の割当一致率が記録される。この再現実行は NFR-4 の再実行性の対象外とする**(中間成果物を読み出す実装では一致率が定義上 100% に固定され、LLM の非決定性を測るという意図が失われるため)
  - [ ] **その2回の実行で、`llm_calls`(NFR-7 の定義。Protocol 呼び出し数であって子プロセス数ではない — 再試行で子プロセス数は2倍にならないため。AR-38)が1回分の2倍になることが確認される**(成果物キャッシュだけを迂回して LLM レスポンスキャッシュを残す実装は、一致率 100% を出すため)
  - [ ] クラスタごとに、そのクラスタが問うている知識の要約が1件出力される
  - [ ] **外部 LLM 呼び出しに失敗があった実行は、下流ステージへ進まず非 0 終了する**。分割呼び出しの
        一部が失敗したまま「割り当てを得られなかった問題を『その他』へ落とす」経路で先へ進んではならない
  - [ ] **実行のサマリに、未分類比率・最大クラスタ比率・LLM 呼び出しの失敗件数の3値が出力され、
        失敗件数が実際の失敗数と一致する**
  - [ ] **レート制限への到達は失敗として数え、下流へ進まず非 0 終了する**(D-091 を 2026-09-25 に撤回)。特別扱いしない。判定に入れられる既知の値が1つも無い(観測できた `status` は `allowed_warning` だけで、これは成功した呼び出しにも付いてくる)まま「待機して継続」を課すと、**成立条件の無い枝を凍結する**ことになるため。終了時は `resetsAt` をログに残し、**人が枠のリセット後に再実行する** — NFR-4 の段階キャッシュが「完了した段は呼び直さない」を既に保証しているので、新しい仕組みは要らない。
  - [ ] **呼び出し1回ごとにタイムアウト上限**(初期値 **10 分**、初回実測後に見直す)を持ち、超過は失敗として数える。**フル処理全体の実経過時間にも上限**(初期値 **12 時間**)を持ち、超過時は非 0 終了する(AR-52。累積待機時間ではなく実経過時間に置く)
  - [ ] **失敗の種別は7種**とし、それぞれの件数が出力される: `SPAWN`(起動失敗)/ `TIMEOUT` / `PARSE`(stdout が JSON にならない)/ `SCHEMA`(`--json-schema` 不適合)/ `TRUNCATED`(応答が最後まで届かなかった。`stop_reason` および `subtype: error_max_turns` で識別する)/ `INCOMPLETE_IDS` / `PROVIDER_ERROR`(`is_error` が真で上のどれにも当たらない。レート制限はここに含まれる)。**`claude` バイナリの不在は起動時に検査してエラー終了する**(NFR-6 によりサンドボックスには存在しないため、ホスト以外では必ず不在になる)
  - [ ] **スキーマに適合した無内容な応答も失敗として数える**(AR-33 の残穴)。**1回の呼び出しに渡した問題 ID のうち、応答に現れなかった ID が1件以上ある呼び出しは失敗**とする。応答にデッキに存在しない ID や重複した ID が含まれる呼び出しも失敗とする。これが無いと、全チャンクについて exit 0 で `{"groups": []}` を返す実装が失敗件数 0 を出し、全問が「その他」へ落ちたまま(排他分割は満たす)exit 0 で下流へ進む。退化ガードは固定フィクスチャにしか掛からず、実データには合格ラインが無い(D-004)ため、この経路は実行時に何にも当たらない
  - [ ] **再試行しない**(D-101 を 2026-09-25 に改訂)。どの失敗種別も1回で確定する。再試行を入れると「失敗件数が実際の失敗数と一致する」の意味が壊れ、`provider_invocations` と `llm_calls` の差の説明も失われる
  - [ ] **要約に現れる主要な語句が、そのクラスタに属する問題文中に実在する**(要約は UI から人間が読む知識の主張であり、実在性を問わないと最初の問題文の先頭を切り出すだけの実装が通る)
- **判定基準の扱い**: M/N・未分類比率・割当一致率に合格ラインは設けず、**記録することを要件とする**。実測前に閾値を置くと、意味のない数値を後から緩めることになるため(D-004)。上の退化ガード3本は閾値ではなく、圧縮を一切していない出力を弾くための下限である。

### R-4: 想起素材の生成
- **Overview**: 各クラスタについて「想起キー」「その手がかりに対する答え」「紛らわしい選択肢との識別ポイント」を生成する。
- **Background / why needed**: 「この単語 + この状況 + この条件が出たら、この答え」という結びつきを作るための中身。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタについて想起キー・答え・識別ポイントの3要素が空でなく出力される
  - [ ] 生成された答えが、そのクラスタに属する問題の正解ラベルと矛盾する件数が 0(検出時は成果物を出さずエラー終了、NFR-1)
  - [ ] 想起キーとして挙げた語句が、そのクラスタの元問題文中に実在する(実在しない語句の混入率 0%)
  - [ ] **各想起キーについて、その語句が他クラスタの問題文にも出現する率が記録される**
  - [ ] **同一の想起キーが複数のクラスタで使われていない**(「AWS」「の」のような、どのクラスタの問題文にも確実に存在する語を選べば実在性チェックは通るが、想起の手がかりにならないため)
  - [ ] **想起キーを構成する語・状況・条件のすべてが他クラスタの問題文にも出現するようなキーの件数が 0 である**(想起キーは組として定義されているため、組が一意でも各要素が汎用語なら手がかりにならない。{AWS, 料金, 設定} と {AWS, 料金, 権限} は重複禁止を通ってしまう)
  - [ ] 識別ポイントが参照する誤答選択肢が、元データの誤答選択肢に実在する(実在率 100%)
  - [ ] **識別ポイントが、誤答選択肢の文面をそのまま引用しただけのものでない**(引用部を除いた説明部分が存在することを機械判定する)
- **想起キーの定義**: 問題文に現れ、そのクラスタの正解を一意に指し示す語・状況・条件の組(D-005)。上2本の基準は、この定義の「一意に指し示す」を観測可能にしたもの。

### R-5: 専門用語グロッサリの生成
- **Overview**: 教材に出現する専門用語を抽出し、各用語の説明を生成する。
- **Background / why needed**: 丸暗記だけでは問題文が変わったときに崩れる。最低限の概念理解を支える側の柱。
- **Priority**: Should
- **Acceptance criteria**:
  - [ ] 教材に出現する専門用語が抽出され、各用語に説明が1件生成される
  - [ ] 説明が元データの公式解説と矛盾する件数が 0。**公式解説を持つ問題が 0 件の場合、照合対象なしとして記録し、合格として報告しない**
  - [ ] グロッサリの音声は想起素材の音声とは別ファイルとして出力される(台本に解説が混ざると、想起素材の効果と切り分けられなくなるため)

### R-6: 音声学習用台本の生成
- **Overview**: 想起素材から、耳だけで成立する一問一答形式の台本を生成する。
- **Background / why needed**: 4択をそのまま読み上げても、選択肢が長い・専門用語が多い問題は聞くだけでは理解できない。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタ分の台本が出力される
  - [ ] **台本に選択肢のラベル列挙が含まれない。ラベル列挙とは、記号(A/B/C/D)・番号(1〜4)・かな(ア〜エ)のいずれであれ、4件の選択肢を並列に提示する形を指す**(機械判定。non-goal「単なる読み上げ」の境界、D-006)
  - [ ] **判定規則が日本語台本と英語台本それぞれに定義されている**(英語では冠詞の "a" やサービス名に含まれる単独の A/B/C/D が正当に現れるため、単独トークンの禁止では正当な台本が落ちる)
  - [ ] 誤答選択肢の内容には、ラベルを使わない比較の形(「X と Y はどちらも〜だが、〜の場合は X」)で言及してよい
  - [ ] 台本の構成が「想起の問いかけ → 間 → 答え → 識別ポイント」の順になっている
  - [ ] **「間」が機械可読なマーカー(SSML の `<break time="3s"/>` に相当するもの)として台本に表現され、TTS がそれを無音として解釈できる**(`【間】` のような地の文の文字列は読み上げられるか読み飛ばされるかのどちらかで、想起の時間にならない)
  - [ ] **1クラスタあたりの台本の推定再生時間が上限を超えない。上限の初期値は3分とし、実測後に見直す**(文字数で定義すると、日本語 1,200 文字と英語 1,200 文字で再生時間が3倍違う)
  - [ ] **上限を超えたクラスタは打ち切らず、クラスタ分割または再生成で対処し、超過したクラスタが列挙される**(末尾を切る実装は全基準を満たしたまま、答えや識別ポイントが途中で切れた音声を出す)

### R-7: 音声ファイルの生成と書き出し
- **Overview**: 台本を TTS で音声化し、携帯端末へ手動転送して意図した順に再生できる形でローカルに書き出す。
- **Background / why needed**: 通勤・散歩・家事・運動の時間に届けるための唯一の経路。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタ分の音声ファイルが生成され、クラスタごと・合計の再生時間が記録される
  - [ ] 一般的な携帯端末の音楽アプリで再生できる形式(mp3 または m4a)で出力される
  - [ ] **各クラスタの音声に、先頭と末尾を除く位置に 3 秒以上の無音区間が1箇所以上あり、その無音の前後いずれにも有音区間が存在することが機械判定される**(「ファイル内に3秒の無音がある」だけでは、各ファイルの末尾に無音を足す後処理が通り、聞こえる成果物は問いかけ→即答えの読み上げに戻る)
  - [ ] **ファイル名がゼロ埋めの連番を先頭に持ち、端末の音楽アプリのファイル名昇順ソートで意図した順に並ぶ**。あわせて m3u プレイリストを出力する
  - [ ] ファイル名またはメタデータからクラスタが特定できる
  - [ ] 音声化に失敗したクラスタが列挙され、部分成功が全成功として扱われない
  - [ ] 教材が日本語・英語のいずれでも音声化でき、どちらの言語で生成したかが記録される
  - [ ] **記録された言語と、実際に使用した TTS のボイス設定が一致する**(言語をメタデータから記録しつつ常に日本語ボイスで読む実装を弾く)

### R-8: 事前/事後テストの出題と学習記録
- **Overview**: 元の4択問題を Web UI 上で出題し、選択結果・正誤・所要時間を記録する。事前と事後の正答率および差分をレポートとして出力する。
- **Background / why needed**: ブリーフの Principles「評価軸は解けるようになったか」を、観測できる形にする唯一の要件。D-003 により、本サイクルの成果物はこの測定器そのものである。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 問題ごとに、選択した選択肢・正誤・所要時間が永続記録される
  - [ ] 事後テストでは選択肢の提示順がシャッフルされる(選択肢の位置を覚えたことによる偽陽性の排除)
  - [ ] **既知の正解を持つフィクスチャに対し、シャッフル提示下で全問正解の入力を与えたとき正答率が 100%、全問誤答の入力を与えたとき 0% になる。正解入力は選択肢の内容または選択肢 ID で同定し、表示位置のインデックスでは与えない。フィクスチャはシャッフルの並びが問題ごとに異なるものとする**(表示位置で入力を組み立てるテストを書くと、シャッフル後の位置とシャッフル前の正解インデックスを突き合わせる採点器でも 100%/0% が出てしまい、実運用では正答率が偶然水準に落ちる)
  - [ ] 事前・事後の正答率と差分を含むレポートが出力される
  - [ ] レポートが、既習フラグ(R-1)の値ごと(`studied` / `unseen` / `unknown`)に正答率を分けて出す
  - [ ] レポートが、この数値の限界を明示する。**hold-out 分割を行っていないため記憶の定着を示すものであって未見問題への転移は示さないこと、および事前テストを受けたこと自体が学習になる(テスト効果)ため、差分には音声学習の効果とテスト効果が分離不能な形で混ざること**の両方を含む
- **測れないことの明示**: hold-out 分割を行わない決定(D-002)により、本サイクルで観測できるのは教材に使った問題の正答率の変化に限られる。

### R-10: 誤答に基づく復習スケジューリング
- **Overview**: テストの誤答が属するクラスタを優先し、次に聞くべき順序を決めた再生リストを出力する。
- **Background / why needed**: 個人の弱点に応じた復習。
- **Priority**: Should
- **Acceptance criteria**:
  - [ ] **クラスタが誤答率の降順に並んだ再生リストが出力される**(「誤答したクラスタが先頭に並ぶ」では、未学習状態の事前テストで誤答が全クラスタに散った時点で全体を指すことになり、ランダム順でも合格する)
  - [ ] 全問正解の場合、空のリストではなく「該当なし」が明示される
  - [ ] 各クラスタの最終学習日時と誤答回数が永続記録される

## Non-functional requirements (criteria)

### NFR-1: 誤学習の防止
- **Criterion (measurable)**: 生成された想起素材・台本・グロッサリ・**クラスタ要約**が主張する内容と、元データの正解ラベル・公式解説との矛盾件数が 0。矛盾を検出した場合、成果物を出力せずエラー終了する。判定は LLM による含意判定で行い、正解の言い換えを矛盾と扱わない。
- **How verified**: (a) 意図的に矛盾を仕込んだフィクスチャで、検出とエラー終了が起きること。(b) **正解を言い換えただけの正しい生成物 n 件に対して、誤検出が 0 件であること**(文字列一致で判定する実装は、言い換えを前提とする R-4 に対してほぼ常にエラー終了する)。(c) **現実的な改変を加えたミューテーション n 件に対する検出率を記録する**(番兵文字列だけを拾う判定器を弾き、偽陰性率を可視化する)。いずれもテストプランに記録。
- **前提の縮退**: 公式解説を持つ問題が 0 件の場合、照合先は正解ラベルのみになる。R-1 / R-2 がその件数を報告するため、承認前にどれだけの照合先があるかを判断できる。

### NFR-2: 教材データの保護
- **Criterion (measurable)**: **取り込んだ実教材の本文**が、Git の追跡対象ファイル・コミット・ログ出力のいずれにも含まれない(該当 0 件)。テスト用に自分で書いた合成フィクスチャ(4択の形をした架空の問題)はこの対象外であり、リポジトリにコミットしてよい。
- **保護境界の定義**(AR-39): この基準が守るのは**リポジトリの追跡対象ファイル・コミット・リポジトリへ書き出すログ**である。本プロダクトが書き出す中間成果物と音声(NFR-4 が永続化を要求しているもの)は教材本文を含むが、それらは `.gitignore` 対象パスにのみ書き出すという既存の規定で境界の内側に置く — 「本プロダクトが書き出すファイル一般」を守る対象と読むと、NFR-4 が要求する永続化そのものを禁じることになる。LLM 呼び出しは教材本文を外部サービスへ送るため(経路が metered API でもサブスクリプション CLI でも同じ)、送信そのものは対象外。加えて **NFR-8 が選んだ CLI 経路は、呼び出しツール自身の会話記録(`~/.claude/projects/**/*.jsonl`)に教材本文の平文コピーをホスト上に残す**。これはリポジトリ外かつ Git 非追跡であり上の criterion を破らないが、**教材本文の第三の平文コピーがホームディレクトリに蓄積されることを承知のうえで許容する**という決定である(D-086)。
- **マスク後に残る言い換えテキストを許容する**(D-098): マスクは `MaterialTextFilter` と同じく**登録済みの逐語文字列**しか消せないため、LLM が言い換えた教材由来テキスト(クラスタ要約・想起素材)は stdout に載り、`docs/test/measurements/*.md` 経由で Git 追跡対象に入る。criterion は「取り込んだ実教材の**本文**」を対象としているので違反ではない。**承知のうえで許容する** — 消すと、不可逆ゲートで人が読む証拠から LLM の応答そのものが消え、AR-42 が恐れた「証拠が空」に近づくため。
- **マスクが保持すべきもの**(AR-42): T-019 / T-020 は「逐語の標準出力/標準エラー」を `docs/test/measurements/*.md` に残すことを要求しており、これは Git 追跡対象なのでマスクが掛かる。マスクは全面置換であってはならず、**argv、終了コード、所要時間、4値トークン、エラー種別、レート制限到達の有無**がマスク後のログに存在することを機械判定する。これが無いと、呼び出しの入出力を全面 `[MASKED]` に置換する実装が NFR-2 も T-019/T-020 も緑にしたまま、不可逆ゲートで人間が読む証拠を空にできる。
- **How verified**: 入出力パスが `.gitignore` の対象であることを起動時に検証するテスト、**外部プロセスへ渡す引数(argv)に教材本文が含まれないことの自動テスト(プロンプト本体は標準入力で渡す。argv は同一ホストの別プロセスから `ps` で読めるため)、**教材本文を含む一時ファイルを作らないことの自動テスト**(AR-40。本文を `/tmp` のファイルへ書いて argv でパスだけ渡す実装は argv テストを緑にするが、同一ホストの別プロセスから読めるという脅威は argv のときと同じまま残る。子プロセス起動中に製品が作成したファイルの集合を fake runner が観測する)、およびリポジトリへ書き出す逐語ログで教材本文がマスクされることの自動テスト**、gitleaks、セキュリティレビュー。

### NFR-3: 認証情報の保護
- **Criterion (measurable)**: **外部サービスの認証情報一般**(LLM・TTS・音声認識の API キー、**Claude Code のサブスクリプション資格情報**(`~/.claude/.credentials.json` の OAuth トークン)、および **Udemy のパスワードとセッションクッキー**)がリポジトリに平文で存在せず、ログ・エラーメッセージにも出力されない(検出 0 件)。環境変数または OS の資格情報ストア経由のみ。
- **ホスト側ツールが自前で管理する資格情報は、保管形式の規定の対象外**(AR-35)。上の「環境変数または OS の資格情報ストア経由のみ」が掛かるのは**本プロダクトが受け取り・保管する**資格情報であって、Claude Code が自分で書く `~/.claude/.credentials.json`(WSL/Linux では平文 JSON)ではない。これを平文禁止と読むと NFR-8 が選んだ既定経路そのものが違反になり、対象外と読むと列挙した意味が消えるため、**本プロダクトはそのファイルを読まない・コピーしない・ログとエラー出力に出さない**ことをこの項目について測る内容とする。
- **How verified**: gitleaks、ログ出力の自動テスト、セッション保存先が `.gitignore` の対象であることのテスト、セキュリティレビュー。

### NFR-4: 段階的な再実行性
- **Criterion (measurable)**: 取り込み・クラスタリング・想起素材・台本・音声の各段階の中間成果物が永続化され、任意の段階から再実行したとき、それより前の段階の **`llm_calls` と `provider_invocations` が**(NFR-7 の定義。HTTP API・CLI サブプロセスの別を問わない)**どちらも 0 である**。R-3 の再現性測定(キャッシュを迂回した再クラスタリング)はこの対象外とする。
- **How verified**: 途中段階を失敗させ、再実行時の **`llm_calls` と `provider_invocations`** を数える自動テスト。
- **R-3 の再現性測定の判定方法**: キャッシュを迂回した2回の再クラスタリングは実 LLM 呼び出しを2回要するため、NFR-6 のネットワーク遮断サンドボックスでは `command` の証拠にできない(スタブは決定的なので一致率が常に 100% になり、測る意味が消える)。この基準は **`artifact` 判定**とし、ホスト上での1回の実測ログをテストプランに記録する。`external` にすると D-003(evidence 待ちを発生させない)と衝突するため採らない。

### NFR-5: 開発基盤と CI
- **Criterion (measurable)**: (a) uv で依存が解決・同期できる、(b) ruff・mypy strict・pytest が全て通る、(c) pre-commit が全ファイルに対して通る、(d) **GitHub Actions のワークフロー定義がリポジトリに存在し、そのうち検査を行う `run` ステップは `bash gate.sh <step>` の形をとり、その `<step>` の集合が `.rein/config.yaml` の `quality_gate` の `kind: command` ステップの集合と一致する**。環境を用意する `run` ステップ(`uv python install` / `uv sync` など)と `uses:` のアクションは同一性の対象外 — 品質ゲートは依存が焼き込まれたイメージで走り、`uv sync` は `network_profile: none` では原理的に動かないため。**部分集合ではなく集合の一致**を求めるのは、CI から検査を1本落としても「同一のコマンド列がゲートで緑」が真になってしまうため、(e) `mkdocs build` が警告なく完了する。Python は 3.13 系。`PyProjectTemplate` から取り込む設定(pyproject.toml の ruff/mypy 設定、.pre-commit-config.yaml、mkdocs.yml、makefile)は本リポジトリ内に写し取り、外部パスを参照しない。
- **How verified**: 品質ゲートの各ステップの終了ステータス。テストプランに記録。
- **実 CI の green はこのサイクルの対象外**: push と pull request は人間承認のみの操作であり、ループは自力で CI の実行結果を取得できない。D-003 が external evidence の待ちを発生させないと決めているため、実 CI が green になることの確認は Out of scope とし、次サイクルの external evidence とする。

### NFR-6: 品質ゲートのネットワーク非依存
- **Criterion (measurable)**: 品質ゲートのコマンドステップが、ネットワーク接続なし(`.rein/config.yaml` の `quality` プロファイルは `network_profile: none`)で成功する。**外部 LLM 呼び出し(HTTP API・CLI サブプロセスの別を問わない)および外部プロセスの起動はテスト内で代替される。`claude` バイナリはサンドボックスイメージに焼かない**(node ランタイムを要するため。ADR-012 が node をイメージに入れないとした決定と一貫する)。CLI 経路のサブプロセス起動点は `adapters/` 配下の1箇所に閉じ、ゲート内では注入した fake runner に差し替わる — これは NFR-8 の (a)〜(e) を機械判定可能にする前提でもある。
- **実 CLI の出力契約をフィクスチャとして固定する**(AR-43): `claude` をイメージに焼かない帰結として、`--json-schema` 適合・`usage` の4値・`total_cost_usd` という新しい既定経路の契約は、ゲート内では fake runner の形としてしか検証されない。fake はパーサが期待する形を返すので、それは自己確認であり、実 CLI と初めて当たるのは T-020 = 不可逆ゲートの向こう側になる。これを避けるため、**実 CLI から採取した生の出力1件を契約フィクスチャとしてリポジトリに置き、採取日と CLI バージョンを併記する。パーサはそのフィクスチャに対するテストを持ち、fake runner の出力がフィクスチャと同一スキーマであることを機械判定する**。採取は教材本文を含まない合成プロンプトで行うため NFR-2 に触れない。
- **How verified**: サンドボックス内での品質ゲート実行が green であること。
- **前提(2026-09-22 に実測済み、AR-15 は解消)**: 配布時の `rein-python` イメージは pytest と uv しか持たず、ruff・mypy・pre-commit・mkdocs をいずれも欠いていた。プロジェクト所有の `.rein/oci/quiz-sift/Containerfile` を作って ruff 0.15.16 / mypy 2.1.0 / mkdocs 1.6.1 を焼き込み、`quality` プロファイルのダイジェストを再ピンした。ネットワーク遮断下で5ステップすべてが green であることを確認済み。
- **`pre-commit` は品質ゲートに入れない**: フックを GitHub から clone するため `network_profile: none` では動作しない。同じ検査を ruff と mypy の直接実行としてゲートに置き、`pre-commit` はホストのコミット時と CI に任せる。

### NFR-7: 処理コストと所要時間の可視化

**呼び出し回数の単位(以下すべてで共通)**: `llm_calls` は `ports/llm.py` の `Llm` 越しの呼び出し数(Protocol のメソッド1回を1と数える)。`provider_invocations` は実際に起動した子プロセスの数で、**分割呼び出しも再試行も個別に数える**。`model_turns` は**モデルとの往復回数**で、エンベロープの `num_turns` の総和とする。
**レート枠を消費するのは `model_turns` であって `provider_invocations` ではない**(AR-57)。`--json-schema` の結果は `StructuredOutput` ツール経由で配送されるため、成功した子プロセス1本の中でモデル往復が 2 回以上起きる(実測: 成功時 `num_turns: 2`、`stop_reason: tool_use`)。**3語をすべて記録し、どの基準がどれを指すかを各基準に明記する**(AR-38)。

- **Criterion (measurable)**: 100〜200問の1回のフル処理について、**次の項目が実行ごとに1つのログへ記録される**(AR-37。項目リストはこの1本だけで、他所に別のリストを置かない):
  - 経過時間、`llm_calls`、`provider_invocations`、**`model_turns`**、**並行度**(同時に起動した子プロセスの最大数。AR-47)
  - **失敗した呼び出しとレート制限で終わった呼び出しのトークンも記録する**(AR-65)。拒否・打ち切り・エラーでも消費したトークンは枠を食うので、**成否の判定より先に `usage` を記録する**(現行 SDK アダプタが同じ規律を持っている)。`result` イベントが来ずに終わった子プロセスは `usage: null` と記録し、件数を別に数える。
  - **レート枠の使用率**(下記)。レート制限で終了した場合はその旨と `resetsAt`
  - 4値トークンの内訳ごとの総量(`input_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens` / `output_tokens`。**2値に畳まない**、AR-29)
  - notional コスト(下記)
- **notional コストは実課金額ではない**。NFR-8 によりサブスクリプション認証で呼ぶため、記録される金額は「同じトークン数を従量課金で処理した場合の名目値」である。ログとレポートの双方に、それが名目値である旨が明記される(出力に `notional` の語を含める)。**実課金額を主張する出力は基準違反とする**。
- **notional コストは自算値と申告値の両方を記録し、その相対差も記録する**(AR-24、AR-36、D-089)。自算値は4値トークンとモデル別単価表から求め、申告値は呼び出し経路の自己申告(`claude -p --output-format json` の `total_cost_usd`)を用いる。片方だけだと「常に 0.0 を返す実装」と「申告値をそのまま転記する実装」のどちらかが必ず通る。これを閉じるため、あわせて次を課す:
  - **単価表は出所を持つ**(取得元 URL または取得日と取得元)。**いずれかの単価が 0 である間は、notional コストを「記録済み」として報告しない**(単価表を全 0 にすれば自算値が常に 0.0 になり、上の2値記録が空振りするため。AR-36)。
  - **既知のトークンベクタと既知の単価表に対する自算値が、手計算した期待値と一致する**ことを `command` で判定する。
- **固定オーバーヘッドの分離**(AR-41): 呼び出し経路自身のシステムプロンプトぶんの入力トークンを、教材由来の入力トークンと区別して記録する。**`claude -p` の `usage` は合計しか返さないため、分離は「合成プロンプトで実測した定数の減算」で行い、その定数・測定日・測定に用いた CLI バージョン・その定数が4値のどのバケツに計上されるかを、単価表と同じ形で出所つきで記録する**。**オーバーヘッドはターン単位で持つ**(AR-57)。システムプロンプトはモデル往復ごとに再送(またはキャッシュ読み)されるので、入力トークン合計 ≈ `num_turns` × オーバーヘッド + 材料 になる。定数は「1ターンあたりのトークン数」として持ち、**判定は `Σ_model (overhead_model × turns_model) + material = 報告された入力トークン合計`**(AR-76。ADR-015 の混成でモデルごとに定数が違うので、単一の `overhead × num_turns` では真になりえない)。**`material` を「合計 − overhead」で算出してはならない**(恒等式になる。AR-51)。材料側は既知長の合成プロンプト k = 1, 2, 3 の反復で独立に較正し、**差が材料の差と一致すること、および切片が記録した定数と一致すること**を判定する とする。`num_turns` はエンベロープが返すので実行時に分かる。
**定数は NFR-8 (e) が定めた argv(有効ツール 0 件・MCP 設定を読まない・空の作業ディレクトリ)で取り直す**(AR-51)。`claude -p` のシステムプロンプトは有効ツールの定義と作業ディレクトリ由来のコンテキストを含むため、2026-09-24 に測った Opus 5 で 14,603 トークン/回 / Haiku 4.5 で 8,506 トークン/回(CLI 2.1.281、新規セッションのため `cache_creation_input_tokens` 側に計上)は **(e) が存在しない時点の値であり、そのままでは使えない**。
  - `material = 合計 − overhead` で算出すると `overhead + material = 合計` は恒等式になり、機械判定が何も落とさない(AR-51)。これを避けるため、**既知の長さの合成プロンプト2本(短・長)で実測し、合計入力トークンの差が材料の差と一致すること、および切片が記録した定数と一致することを判定する**。定数は単価表と同じく測定日・CLI バージョン・計上先のバケツを出所として持つ。
- **上限値は金額ではなく、サブスクリプションのレート枠として、初回実測後に設定する**(D-021 を書き換え)。notional コストには課金上の意味が無く、実際に処理を止めるのはレート枠であるため。**本サイクルでは上の項目を記録することだけを要件とし、合格ラインは設けない**。
- **レート枠の使用率を、フル処理の前後で記録する**(2026-09-25 実測により AR-37 の「観測手段が無い」は解消した)。`stream-json` の `rate_limit_event` が `rate_limit_info` として `status` / `rateLimitType` / `utilization` / `resetsAt` と、`unifiedWindows` の `five_hour` / `seven_day` それぞれの `utilization` と `resetsAt` を返す。**フル処理の開始時と終了時の両方について、両ウィンドウの `utilization` と `resetsAt` を記録する**。これにより「単一のウィンドウ内で完走したか」は `resetsAt` が処理中に進んだかどうかで**反証可能に判定できる**(定数 `true` を書く実装は、記録した `resetsAt` と突き合わせて落ちる)。**枠を使い切らなくても使用率が読めるので、D-085 が「実測しない」と決めた対象のうち、レート枠の形と残量については観測で答えが出る。**
- **How verified**: 実行ログに上記の項目と算出根拠が存在することの自動テストと、初回実測値のテストプランへの記録。

### NFR-8: 外部サービスの利用が従量課金を伴わないこと

- **この要件の対象**(AR-44): **本プロダクトの製品コードの実行**に限る。本ハーネス自身の LLM 利用(開発時に `rein build` が起動する implementer / reviewer / fixer)は対象外であり、それが従量課金であることは変わらない。所有者が課した制約は製品の実行についてのものである。
- **metered 認証変数の集合**(AR-48。以下で「metered 認証変数」と呼ぶものの定義。(f) が参照する): `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL`、`CLAUDE_CODE_USE_BEDROCK`、`CLAUDE_CODE_USE_VERTEX`、`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_SESSION_TOKEN`、`AWS_PROFILE`、`AWS_REGION`、`GOOGLE_APPLICATION_CREDENTIALS`、`GOOGLE_CLOUD_PROJECT`、`CLOUD_ML_REGION`。この集合は**許可集合とは別物**であり、両方を要件が列挙する。
- **Criterion (measurable)**: 製品コードの実行が、**従量課金(metered)される外部サービス経路を一切取らない**。現時点で該当するのは LLM のみ(TTS はローカル OSS、ADR-004)だが、基準は外部サービス一般に課す。次の (a)〜(g) を判定する((a)〜(f) は**いずれも 0 件**、(g) は argv の形の一致)。
  - **(a) metered SDK が実行時に読み込まれない**: **新規のインタプリタ(サブプロセス)で**(AR-50。`sys.modules` はプロセス全域なので、(c) が認める「テストコードからの直接構築」のテストと同一プロセスで判定すると順序依存で赤になり、実装者は `sys.modules.pop` かテスト削除で逃げる)、**親環境に metered 認証変数が入っており、かつ `anthropic` が import 可能な状態で**(AR-31)、既定構成でパイプラインを1回走らせた直後、`sys.modules` に `anthropic` が現れる件数が 0。
    **positive control を必ず置く**: 判定に使う実行で `build_default_llm()` が実際に呼ばれ、`llm_calls ≥ 1` であることを同時に要求する。これが無いと、`Llm` に一度も触れないサブコマンド(取り込みなど)を走らせるだけで無条件に緑になる。
    **negative control を必ず置く**: `composition.build_default_llm()` が返すクラスを SDK アダプタに差し替えたとき、**この判定が赤くなること**をテストで要求する。これが無いと、`claude` バイナリ不在や最小ホーム不在の起動時検査でパイプラインが LLM を1つも組み立てないまま終わり、**既定が SDK アダプタのままでも緑になる**(R-3 の退化ガードと契約フィクスチャには negative control を課しているのに、NFR-8 の中心基準にだけ無いという非対称を消す)。**`anthropic` が import 可能でない場合、このテストは skip せず失敗とする**(AR-49。`anthropic` は optional extra であり、NFR-6 が固定した `quality` イメージには焼かれておらずネットワーク遮断下で追加もできないため、skip を許すと「条件が成立しないので緑」が復活する)。import 可能性は、`sys.path` に**スタブの `anthropic` パッケージを置く**ことで満たす — 実 SDK をイメージに焼く必要はなく、判定に必要なのは「読み込まれたかどうか」だけである。
  - **(b) 子プロセスへ渡す環境は許可リストで構築する**(AR-30): 子プロセスへ渡す環境は**明示的に構築した辞書のみ**とし、**親環境を継承しない**。渡す変数名の集合が、次の**許可集合と一致する**(部分集合ではない)ことを機械判定する:
    - **`HOME`、`PATH`、`LANG`、`TZ` の4つのみ**。
    - **`HOME` は、その実行のために用意した専用の最小ホームを指す**。そこに置くのはサブスクリプション資格情報(`.claude/.credentials.json`)だけとし、**`settings.json`・`CLAUDE.md`・MCP 設定・プラグイン・hooks 定義をいずれも置かない**。呼び出し元のホームをそのまま渡してはならない。これは `HOME` を許可せざるを得ないこと(渡さないと (f) の「metered 認証が無い状態で完走」が成立しない)と、**ホスト設定の `env` ブロックや `apiKeyHelper` が `HOME` 一本を通って metered 経路を復活させうること**(Claude Code のユーザ設定は毎セッション適用される)を同時に満たす唯一の形である。**判定するのは「製品が `HOME` 配下に作成したファイルが 0 件であること」**(D-096)。文字どおりの「1ファイルだけ」は、`claude` が `$HOME/.claude.json`・`.claude/projects/**/*.jsonl`(D-086 が許容した教材本文の置き場そのもの)・`statsig/` を必ず書くため **2回目の起動から必ず偽**になる。測る対象は製品の振る舞いであって CLI の振る舞いではない。資格情報を**置くのは人間**であり(ADR-014)、製品は読みもコピーもせずパスを渡して存在を確かめるだけなので、NFR-3 とも衝突しない。
    - 親環境に metered 認証変数の値が入っている状態でテストする(未設定の環境で 0 件になるのは、実装が何もしていなくても成立する)。
    - **拒否リスト方式は採らない** — `ANTHROPIC_API_KEY` を除いても Bedrock / Vertex の切り替え変数が残り、列挙の穴がそのままテストの穴になるため。許可リストの側も、**要件がこの集合を列挙している**ことで実装側の定数を読みに行く自己確認を避ける。
  - **(c) 既定実装の選択点が1箇所に固定され、その形が AST で判定できる**(AR-31、AR-45): **`quiz_sift/composition.py` の `build_default_llm()` を既定 `Llm` の唯一の選択点とする**。その関数の本体は **`return` 文1つ**であり、右辺は**クラス名の直接呼び出し**とし、関数内に `if` / `match` / `try` / 添字アクセス / 属性の動的解決 / `os.environ` の参照 / ファイル読み出し / `importlib` をいずれも含まない。「分岐しない単一の静的式」だけでは、レジストリ辞書(`_REGISTRY["default"]()`)や環境変数添字(`_IMPLS[os.environ.get(...)]()`)が字面を満たして通る。Anthropic SDK アダプタ(`adapters/llm_anthropic.py`)は**コードに残してよいが**、**opt-in の唯一の形はテストコードからの直接構築**とし、製品の実行経路からは到達不能とする。環境変数・設定ファイル・プラグイン機構による自動切り替えは opt-in ではない。
  - **(d) metered エンドポイントへの発行経路が、製品の全入口から到達不能**(AR-31): **`pyproject.toml` が宣言するコンソールスクリプトが1つだけであること**を機械判定し、そのすべての入口から到達可能な import グラフに、metered API のホスト(`api.anthropic.com` 等)へ HTTP を発行しうるモジュールが 0 件であることを静的判定する。対象を「既定経路」に限ると、第2のコンソールスクリプトで SDK アダプタを直接構築する実装が (a)(c)(d) を緑のまま素通りする。(c) が動的 import を禁じることでこの走査の有効性が担保される。
  - **(e) 子プロセスの argv の形を固定する**(AR-32): 「無効化指定が argv に含まれること」では `--disallowedTools Bash` 1本で満たせてしまい、Read / Write / Edit / WebFetch が残る — (e) 自身が述べる脅威(第三者テキストの注入で子エージェントがホスト上のファイルを読み書きする、教材本文を外部 URL へ送る)はそのまま残る。次の4点を機械判定する:
    1. **有効ツールの集合が `{"StructuredOutput"}` と一致する**(2026-09-25 実測)。`--allowedTools ''` は無効果だが、**`--settings` の `permissions.deny` に全ツール名を列挙すると `init` イベントの `tools` が `StructuredOutput` の1本だけになり、それでも呼び出しは成功する**。`StructuredOutput` は `--json-schema` の結果を配送する機構そのものなので、脅威モデル上は「有効ツール 0 件」と等価である(ファイルシステム読み書き・ネットワーク到達・サブエージェント起動のいずれもできない)。
       **部分集合ではなく一致**を求める(AR-30 の教訓)。素の状態では `Glob` と `Grep` — どちらもファイルシステムを読む — が有効であり、`deny` の列挙から漏れると残る。有効ツールの集合は他フラグの有無でも動く(実測で 19 / 22 / 1 と変わった)ので、**`deny` の列挙が正しいことを列挙の側から保証してはならない**。判定は `init` イベントの `tools` 配列に対する一致判定とする。
       ゲート内では実 CLI が無いので argv の形しか見えない。**`init.tools` が実際に `{"StructuredOutput"}` になることはホスト実測の `artifact` 証拠として1本置く**(AR-43 と同じ自己確認の穴がここにも開くため)。
    2. **権限バイパスの指定(`--dangerously-skip-permissions` 等)が含まれない**。
    3. **外部の MCP 設定を読まない指定が含まれる**。
    4. **作業ディレクトリが、その実行のために作った空ディレクトリである**。「教材・成果物・リポジトリの外側」だけでは `cwd = $HOME` が通り、`~/.ssh` や `~/.aws` を子エージェントのプロジェクトルートに据えることになる。
  - **(g) 出力形式は `stream-json` とする**: `--output-format stream-json --verbose` と `--json-schema` を併用し、`--max-turns` は 3 以上とする(2026-09-25 実測: `--max-turns 1` では構造化出力にターンが足りず `error_max_turns` で `result` が `null` になる)。これにより `init` イベントの `tools`((e)1 の判定対象)と `apiKeySource`、および `rate_limit_event`(NFR-7 が記録するレート枠の使用率)が本番経路でそのまま観測できる。`--output-format json` では3つとも取れない。
  - **(f) metered 認証が無い状態で完走する**: フル処理の実測(T-020)を、**上で列挙した metered 認証変数をいずれも環境に持たない状態**で実行し、完走したことが実行ログに残る。ログは実行時の環境変数名の一覧(値は伏せる、NFR-3)を含み、それらが存在しなかったことが機械判定できる。
  - **(b) と (f) は対で意味を持つ**。(b) は「あっても渡さない」、(f) は「無くても完走する」。(b) 単独だと「env は掃除するが別経路で課金される」が通り、(f) 単独だと「たまたま無かっただけ」が通る。
- **How verified**: (a)〜(e) は品質ゲート内の自動テスト。**ネットワークも実 `claude` バイナリも不要** — サブプロセス起動点は `adapters/` 配下の1箇所に閉じて注入可能にし、ゲート内では fake runner がその argv・env・作業ディレクトリ・起動中に作成されたファイルを観測する(NFR-6)。(a) のみ新規インタプリタで走らせる。(f) は T-020 のフル実測ログに対する `artifact` 判定。
- **この基準が測っていないこと**(D-087 で人間が承知のうえ選んだ範囲 + 2巡目のレビューで明らかになった残余):
  - (a)〜(f) はいずれも「**metered 経路を取らなかった**」ことの否定的証拠であり、「サブスクリプション枠で処理され課金が発生しなかった」ことの**肯定的証拠ではない**。実行時に `--output-format stream-json` の `init` イベントが返す `apiKeySource` を毎回検証すれば肯定的証拠になるが(2026-09-24 に実測、値は `none`)、**本サイクルでは課さないと決めた**。
  - **最小ホームが実際にホスト設定を遮断できるかは未検証**。(b) の最小ホーム規定は、Claude Code がユーザ設定・hooks・MCP・`CLAUDE.md` を `HOME` 起点で読むという前提に立っている。**それ以外の起点(システム全体の管理設定、実行ファイルに同梱されたプラグイン)から指示や権限が入る経路は、製品コードからは塞げない**。
  - 実際に課金が発生しなかったことの確認は課金画面の目視であり、本ループは行わない(Out of scope)。

## Open questions

- **中心仮説の検証は本サイクルでは行わない**。hold-out 分割をしない決定(D-002)により、「100問の背後にある共通パターンへ圧縮すれば、限られた時間でも4択試験への対応力が高まる」という仮説は、本サイクルでは支持も反証もできない。R-8 が記録するのは、教材として使った問題そのものの正答率の変化に限られ、そこにはテスト効果も混ざる。仮説の検証は、測定設計を含む後続サイクルの課題として残る。
- **NFR-7 の上限は、金額ではなくレート枠として未定**。NFR-8 により従量課金が発生しないため、金額の上限には課金上の意味が無い。実際に処理を止めるのはサブスクリプションのレート枠であり、本サイクルでは記録することだけを要件とし、上限は次サイクルで設定する。
- **Claude Pro のレート枠が本番規模を賄えるかは未検証**(D-085 で、実測せず凍結すると人間が決めた)。フル処理1回は `generate_recall` 175 回、`check_entailment` 350〜500 回、`describe_term` が抽出語句ぶん、`classify_clusters` 4回 ×2 で、**合計 500〜1000 回**の呼び出しと見込まれる。賄えなかった場合の処置はいずれも上流を動かす: 上位プランへの移行は制約の意図(支出を増やさない)の再判断、複数ウィンドウへの分割は NFR-7 の「1回のフル処理」の定義と T-020 の A-1、呼び出し回数の削減は NFR-1 の照合対象と R-3 の受入基準。**T-020 で判明した時点で `/revise` に戻る可能性がある**ことを承知のうえで凍結する。
- **`claude` CLI のバージョンが凍結されない**。品質ゲートの依存はサンドボックスイメージに焼かれる(ADR-001)が、CLI はホストに置かれ自動更新される。`--json-schema` と `--output-format json` の挙動はホスト依存であり、本サイクルでは 2.1.281 で実測した値に依拠する。
- **Udemy の利用規約の解釈**は本人の確認に依拠しており、本ループは独立に検証していない。規約の解釈が変わった場合、R-2 は丸ごと影響を受ける。
- **品質ゲートのイメージがツール一式を含むかは未検証**(AR-15)。`/tasks` の `rein baseline measure` で実測し、不足があればイメージ更新を mandate 凍結前に行う。
