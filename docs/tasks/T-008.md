  判定: `pytest -q tests/ingest/test_studied.py::test_per_question_flag_overrides_deck_default`

## Automated-test approach (the basis for the green decision)

- **Test kind**: unit / integration
- **Test file(s)**: `tests/ingest/test_dedup.py`, `tests/ingest/test_report.py`, `tests/ingest/test_studied.py`, `tests/ingest/test_validate.py`
- **Test target / cases** — 各ノードについて **何を壊すと赤になるか**:

  - **A-1**: accepted と rejected を別々に足し込む実装(保存則を後から検査する形)→ 構築できず赤
  - **A-2**: パーサが厳しすぎて正常系でも除外が出る実装 → 赤
  - **A-3**: 除外理由を1種類に潰す / 件数だけ返して ID を出さない実装 → 赤
  - **A-4**: 完全一致だけで ratio を見ない実装 → 赤(0.95 の近傍フィクスチャで検出されない)
  - **A-5**: 解説の有無を数えない実装 → 赤
  - **A-6**: 既習フラグ列を読まず常にデッキ既定へ落とす実装 → 赤

> ノード ID は「その名前のテストが存在すること」までしか強制しない — **空の本体(`pass`)でも exit 0 になる**
> ことは実測で確かめてある。上の行は、実装者とレビュアーがその空白を見つけるための唯一の非循環な手掛かりで、
> 最終的な防御はタスク DoD の `review` ステップ(コードレビュアーがテストを読む)。
