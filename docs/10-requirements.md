# Requirements

> `/req` generates/updates this, sounding out from `docs/00-product-brief.md`.
> Finalized once a human approves at **the mandate**. Changes after approval need re-approval.

## Summary

4択問題集を AI が分析し、背後にある知識・出題パターン・紛らわしい選択肢の違いへ圧縮したうえで音声化する。
机に向かえない時間を復習に使えるようにし、学習の前後で正答率を測定して記録する。
問題の取り込みから音声の書き出しまでを Python CLI が担い、テスト出題と学習記録は Web UI が担う。

## 優先度と acceptance の関係

Priority(Must / Should / Could)は **実装の着手順序** を表し、未達を許す指定ではない。
`.rein/plan.yaml` に凍結された 18 本の claim はすべて acceptance の判定対象であり、
未達の claim が1本でもあれば acceptance は通らない。範囲を削る場合は mandate の承認前に
要件ごと落とす(`/revise` ではなく承認前の縮小)。R-9(音声回答と AI 採点)はこの経路で
承認前に落とした要件であり、**R-9 は欠番**である。採番を詰めないのは、決定の履歴を
追えるようにするため。

## List of things to achieve

### R-1: 問題データの取り込みと正規化
- **Overview**: 4択問題(問題文・選択肢4件・正解・既習フラグ・あれば公式解説)の集合を構造化ファイルから読み込み、内部形式へ正規化する。
- **Background / why needed**: 以降のすべての工程の入力。ここで欠損を素通りさせると、圧縮も測定も静かに壊れる。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 100〜200問を読み込み、取り込めた問題すべてについて問題文・選択肢4件・正解1件が欠落なく保持される
  - [ ] 選択肢数が4でない、正解が特定できない、ID が重複する問題は取り込み時に個別に列挙され、除外件数が報告される
  - [ ] 取り込み件数 + 除外件数 = 入力件数 が常に成立する
  - [ ] **正常系フィクスチャ(全問が妥当な形式)に対して、除外件数が 0 になる**(パーサが厳しすぎて大半を捨てても保存則だけは成立してしまうため)
  - [ ] 文面がほぼ同一の重複問題が検出され、件数が報告される
  - [ ] **入力形式が既習フラグの列を持ち、その値(`studied` / `unseen`)が取り込み時に読み取られる**。個別の指定が無い問題にはセット単位の指定(R-11)が適用され、**個別指定もセット指定も無い場合に限り** `unknown` として記録される。`unknown` を `studied` / `unseen` のどちらかで埋めることはしない
  - [ ] **公式解説を持つ問題の件数と持たない問題の件数が報告される**(NFR-1 の照合先がどれだけあるかを承認前に知るため)

### R-2: Udemy からの問題自動抽出
- **Overview**: Udemy の問題集ページからヘッドレスブラウザのスクリプトで問題文・選択肢・正解・解説を抽出し、R-1 の入力形式で書き出す。
- **Background / why needed**: 教材を手作業で起こす手間が続くと、100〜200問規模の運用が成立しない。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 1模試分のページから、抽出できた問題数と抽出できなかった問題数の両方が報告される
  - [ ] 抽出結果が R-1 の入力形式として妥当であることが、書き出し時に検証される
  - [ ] ページ構造の変化などで抽出できなかった箇所は、黙って空文字で埋めずエラーとして列挙される
  - [ ] **人手で正解を確認した10件のゴールデンセットに対し、抽出した正解ラベルの一致率が 100% である。この10件は、受験者の選択と正解が異なる問題を3件以上含む**(正答した問題だけで構成すると、自分の選択を正解として拾う実装がそのまま 100% になる)
  - [ ] **正解と判定した根拠の要素種別が記録され、全問で同一種別である**(ゴールデンセットの10件だけを特別扱いする実装を弾く)
  - [ ] **各問題について、どの要素を根拠に正解と判定したかが記録され、目視で追跡できる**(結果ページは自分が選んだ選択肢と正解の両方を強調するため、取り違えると誤った正解ラベルが取り込まれ、NFR-1 がそれを正しい生成物のエラーとして扱う向きに働く)
  - [ ] **公式解説を取得できた問題数と、できなかった問題数が報告される**
  - [ ] 抽出した問題文が、`.gitignore` の対象であることを起動時に検証したパスにのみ書き出される(NFR-2 と対)

### R-3: 類似問題のクラスタリング(圧縮)
- **Overview**: 問題群を、背後にある知識・出題パターンごとの排他クラスタへまとめる。
- **Background / why needed**: 「100問を100個の知識として覚えない」というプロダクトの中心にある考え方の実体。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] N 問の入力に対しクラスタ数 M が出力され、M / N が記録される
  - [ ] すべての問題がちょうど1つのクラスタに属する(排他分割)。分類できない問題は「その他」クラスタとして明示され、その比率が記録される
  - [ ] **退化ガードの判定に用いる固定フィクスチャが、既知の 5 グループから成り、各グループが3問以上を持つものとして定義されている**(フィクスチャの構成が未定義だと、正解となるグループ構造が無いため下の基準は何とでも満たせる)
  - [ ] **そのフィクスチャに対し、最大クラスタに属する問題数が全体の 50% を超えない**
  - [ ] **そのフィクスチャに対し、「その他」クラスタの比率が 20% 以下である**
  - [ ] 実データに対する最大クラスタ比率と「その他」比率が記録される(合格ラインは設けない)
  - [ ] 各クラスタに、属する全問題 ID の一覧が付随する
  - [ ] **キャッシュを迂回して再クラスタリングした2回の実行について、問題の割当一致率が記録される。この再現実行は NFR-4 の再実行性の対象外とする**(中間成果物を読み出す実装では一致率が定義上 100% に固定され、LLM の非決定性を測るという意図が失われるため)
  - [ ] **その2回の実行で、外部 API 呼び出し回数が1回分の2倍になることが確認される**(成果物キャッシュだけを迂回して LLM レスポンスキャッシュを残す実装は、一致率 100% を出すため)
  - [ ] クラスタごとに、そのクラスタが問うている知識の要約が1件出力される
  - [ ] **要約に現れる主要な語句が、そのクラスタに属する問題文中に実在する**(要約は UI から人間が読む知識の主張であり、実在性を問わないと最初の問題文の先頭を切り出すだけの実装が通る)
- **判定基準の扱い**: M/N・未分類比率・割当一致率に合格ラインは設けず、**記録することを要件とする**。実測前に閾値を置くと、意味のない数値を後から緩めることになるため(D-004)。上の退化ガード3本は閾値ではなく、圧縮を一切していない出力を弾くための下限である。

### R-4: 想起素材の生成
- **Overview**: 各クラスタについて「想起キー」「その手がかりに対する答え」「紛らわしい選択肢との識別ポイント」を生成する。
- **Background / why needed**: 「この単語 + この状況 + この条件が出たら、この答え」という結びつきを作るための中身。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタについて想起キー・答え・識別ポイントの3要素が空でなく出力される
  - [ ] 生成された答えが、そのクラスタに属する問題の正解ラベルと矛盾する件数が 0(検出時は成果物を出さずエラー終了、NFR-1)
  - [ ] 想起キーとして挙げた語句が、そのクラスタの元問題文中に実在する(実在しない語句の混入率 0%)
  - [ ] **各想起キーについて、その語句が他クラスタの問題文にも出現する率が記録される**
  - [ ] **同一の想起キーが複数のクラスタで使われていない**(「AWS」「の」のような、どのクラスタの問題文にも確実に存在する語を選べば実在性チェックは通るが、想起の手がかりにならないため)
  - [ ] **想起キーを構成する語・状況・条件のすべてが他クラスタの問題文にも出現するようなキーの件数が 0 である**(想起キーは組として定義されているため、組が一意でも各要素が汎用語なら手がかりにならない。{AWS, 料金, 設定} と {AWS, 料金, 権限} は重複禁止を通ってしまう)
  - [ ] 識別ポイントが参照する誤答選択肢が、元データの誤答選択肢に実在する(実在率 100%)
  - [ ] **識別ポイントが、誤答選択肢の文面をそのまま引用しただけのものでない**(引用部を除いた説明部分が存在することを機械判定する)
- **想起キーの定義**: 問題文に現れ、そのクラスタの正解を一意に指し示す語・状況・条件の組(D-005)。上2本の基準は、この定義の「一意に指し示す」を観測可能にしたもの。

### R-5: 専門用語グロッサリの生成
- **Overview**: 教材に出現する専門用語を抽出し、各用語の説明を生成する。
- **Background / why needed**: 丸暗記だけでは問題文が変わったときに崩れる。最低限の概念理解を支える側の柱。
- **Priority**: Should
- **Acceptance criteria**:
  - [ ] 教材に出現する専門用語が抽出され、各用語に説明が1件生成される
  - [ ] 説明が元データの公式解説と矛盾する件数が 0。**公式解説を持つ問題が 0 件の場合、照合対象なしとして記録し、合格として報告しない**
  - [ ] グロッサリの音声は想起素材の音声とは別ファイルとして出力される(台本に解説が混ざると、想起素材の効果と切り分けられなくなるため)

### R-6: 音声学習用台本の生成
- **Overview**: 想起素材から、耳だけで成立する一問一答形式の台本を生成する。
- **Background / why needed**: 4択をそのまま読み上げても、選択肢が長い・専門用語が多い問題は聞くだけでは理解できない。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタ分の台本が出力される
  - [ ] **台本に選択肢のラベル列挙が含まれない。ラベル列挙とは、記号(A/B/C/D)・番号(1〜4)・かな(ア〜エ)のいずれであれ、4件の選択肢を並列に提示する形を指す**(機械判定。non-goal「単なる読み上げ」の境界、D-006)
  - [ ] **判定規則が日本語台本と英語台本それぞれに定義されている**(英語では冠詞の "a" やサービス名に含まれる単独の A/B/C/D が正当に現れるため、単独トークンの禁止では正当な台本が落ちる)
  - [ ] 誤答選択肢の内容には、ラベルを使わない比較の形(「X と Y はどちらも〜だが、〜の場合は X」)で言及してよい
  - [ ] 台本の構成が「想起の問いかけ → 間 → 答え → 識別ポイント」の順になっている
  - [ ] **「間」が機械可読なマーカー(SSML の `<break time="3s"/>` に相当するもの)として台本に表現され、TTS がそれを無音として解釈できる**(`【間】` のような地の文の文字列は読み上げられるか読み飛ばされるかのどちらかで、想起の時間にならない)
  - [ ] **1クラスタあたりの台本の推定再生時間が上限を超えない。上限の初期値は3分とし、実測後に見直す**(文字数で定義すると、日本語 1,200 文字と英語 1,200 文字で再生時間が3倍違う)
  - [ ] **上限を超えたクラスタは打ち切らず、クラスタ分割または再生成で対処し、超過したクラスタが列挙される**(末尾を切る実装は全基準を満たしたまま、答えや識別ポイントが途中で切れた音声を出す)

### R-7: 音声ファイルの生成と書き出し
- **Overview**: 台本を TTS で音声化し、携帯端末へ手動転送して意図した順に再生できる形でローカルに書き出す。
- **Background / why needed**: 通勤・散歩・家事・運動の時間に届けるための唯一の経路。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 全クラスタ分の音声ファイルが生成され、クラスタごと・合計の再生時間が記録される
  - [ ] 一般的な携帯端末の音楽アプリで再生できる形式(mp3 または m4a)で出力される
  - [ ] **各クラスタの音声に、先頭と末尾を除く位置に 3 秒以上の無音区間が1箇所以上あり、その無音の前後いずれにも有音区間が存在することが機械判定される**(「ファイル内に3秒の無音がある」だけでは、各ファイルの末尾に無音を足す後処理が通り、聞こえる成果物は問いかけ→即答えの読み上げに戻る)
  - [ ] **ファイル名がゼロ埋めの連番を先頭に持ち、端末の音楽アプリのファイル名昇順ソートで意図した順に並ぶ**。あわせて m3u プレイリストを出力する
  - [ ] ファイル名またはメタデータからクラスタが特定できる
  - [ ] 音声化に失敗したクラスタが列挙され、部分成功が全成功として扱われない
  - [ ] 教材が日本語・英語のいずれでも音声化でき、どちらの言語で生成したかが記録される
  - [ ] **記録された言語と、実際に使用した TTS のボイス設定が一致する**(言語をメタデータから記録しつつ常に日本語ボイスで読む実装を弾く)

### R-8: 事前/事後テストの出題と学習記録
- **Overview**: 元の4択問題を Web UI 上で出題し、選択結果・正誤・所要時間を記録する。事前と事後の正答率および差分をレポートとして出力する。
- **Background / why needed**: ブリーフの Principles「評価軸は解けるようになったか」を、観測できる形にする唯一の要件。D-003 により、本サイクルの成果物はこの測定器そのものである。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] 問題ごとに、選択した選択肢・正誤・所要時間が永続記録される
  - [ ] 事後テストでは選択肢の提示順がシャッフルされる(選択肢の位置を覚えたことによる偽陽性の排除)
  - [ ] **既知の正解を持つフィクスチャに対し、シャッフル提示下で全問正解の入力を与えたとき正答率が 100%、全問誤答の入力を与えたとき 0% になる。正解入力は選択肢の内容または選択肢 ID で同定し、表示位置のインデックスでは与えない。フィクスチャはシャッフルの並びが問題ごとに異なるものとする**(表示位置で入力を組み立てるテストを書くと、シャッフル後の位置とシャッフル前の正解インデックスを突き合わせる採点器でも 100%/0% が出てしまい、実運用では正答率が偶然水準に落ちる)
  - [ ] 事前・事後の正答率と差分を含むレポートが出力される
  - [ ] レポートが、既習フラグ(R-1)の値ごと(`studied` / `unseen` / `unknown`)に正答率を分けて出す
  - [ ] レポートが、この数値の限界を明示する。**hold-out 分割を行っていないため記憶の定着を示すものであって未見問題への転移は示さないこと、および事前テストを受けたこと自体が学習になる(テスト効果)ため、差分には音声学習の効果とテスト効果が分離不能な形で混ざること**の両方を含む
- **測れないことの明示**: hold-out 分割を行わない決定(D-002)により、本サイクルで観測できるのは教材に使った問題の正答率の変化に限られる。

### R-10: 誤答に基づく復習スケジューリング
- **Overview**: テストの誤答が属するクラスタを優先し、次に聞くべき順序を決めた再生リストを出力する。
- **Background / why needed**: 個人の弱点に応じた復習。
- **Priority**: Should
- **Acceptance criteria**:
  - [ ] **クラスタが誤答率の降順に並んだ再生リストが出力される**(「誤答したクラスタが先頭に並ぶ」では、未学習状態の事前テストで誤答が全クラスタに散った時点で全体を指すことになり、ランダム順でも合格する)
  - [ ] 全問正解の場合、空のリストではなく「該当なし」が明示される
  - [ ] 各クラスタの最終学習日時と誤答回数が永続記録される
  - [ ] **出力が m3u プレイリスト、またはトラック番号を焼いたファイル名として書き出され、携帯端末の音楽アプリがその順序で再生できる**(順序を計算しても端末に届かなければ、実際に聞く順序は端末のソート順になる)
- **有効性の限界**: 本サイクルで得られる学習ログは事前・事後の2回分のみであり、スケジューリングの有効性は検証できない。動作の確認までにとどまる。

### R-11: 複数教材セットの管理
- **Overview**: 複数の問題集(デッキ)を混在させずに保持し、選択して使える。
- **Background / why needed**: 教材によって言語が異なり(日本語・英語)、学習記録もセット単位で分ける必要がある。
- **Priority**: Should
- **Acceptance criteria**:
  - [ ] 2セット以上を同時に保持でき、あるセットの問題が別セットのクラスタに混入しない
  - [ ] 学習記録・レポートがセット単位で分離される
  - [ ] セットごとに言語が記録され、音声生成時に参照される。**日本語セットの本文に英語のサービス名・用語が混在することを前提とし、混在テキストを TTS へ渡せる**
  - [ ] **セット単位で既習/初見を指定でき、問題個別の指定があればそれがセット指定を上書きする**(Udemy のページに既習の情報は無く、R-2 の抽出では既習フラグの値が得られない。デッキ単位の指定が無ければ、全問が `unknown` になり D-015 が要求する集計の分離が達成できない)

### R-12: Web UI
- **Overview**: テスト出題、学習記録の閲覧、再生リストの確認を行うローカル Web アプリケーション。
- **Background / why needed**: 画面上の4択で出題すると決めたため、UI が必須になる。
- **Priority**: Must
- **Acceptance criteria**:
  - [ ] ローカルで起動し、ブラウザからテストの実施・結果の閲覧ができる
  - [ ] CLI が生成した成果物(クラスタ・想起素材・音声)を読み、UI 側で再生成しない
  - [ ] **テスト中の回答がサーバ側の学習記録ストアへ永続化され、ブラウザを閉じても失われない。ブラウザ内ストレージのみに保持する実装は要件を満たさない**(R-8 のレポート、R-10 の再生リスト、R-11 のセット別集計はいずれも CLI 側から同じ記録を読む)
  - [ ] **学習記録ストアが CLI と UI の双方から読み書きでき、その所在と形式が一箇所で定義されている**

## Non-functional requirements (criteria)

### NFR-1: 誤学習の防止
- **Criterion (measurable)**: 生成された想起素材・台本・グロッサリ・**クラスタ要約**が主張する内容と、元データの正解ラベル・公式解説との矛盾件数が 0。矛盾を検出した場合、成果物を出力せずエラー終了する。判定は LLM による含意判定で行い、正解の言い換えを矛盾と扱わない。
- **How verified**: (a) 意図的に矛盾を仕込んだフィクスチャで、検出とエラー終了が起きること。(b) **正解を言い換えただけの正しい生成物 n 件に対して、誤検出が 0 件であること**(文字列一致で判定する実装は、言い換えを前提とする R-4 に対してほぼ常にエラー終了する)。(c) **現実的な改変を加えたミューテーション n 件に対する検出率を記録する**(番兵文字列だけを拾う判定器を弾き、偽陰性率を可視化する)。いずれもテストプランに記録。
- **前提の縮退**: 公式解説を持つ問題が 0 件の場合、照合先は正解ラベルのみになる。R-1 / R-2 がその件数を報告するため、承認前にどれだけの照合先があるかを判断できる。

### NFR-2: 教材データの保護
- **Criterion (measurable)**: **取り込んだ実教材の本文**が、Git の追跡対象ファイル・コミット・ログ出力のいずれにも含まれない(該当 0 件)。テスト用に自分で書いた合成フィクスチャ(4択の形をした架空の問題)はこの対象外であり、リポジトリにコミットしてよい。
- **How verified**: 入出力パスが `.gitignore` の対象であることを起動時に検証するテスト、gitleaks、セキュリティレビュー。

### NFR-3: 認証情報の保護
- **Criterion (measurable)**: **外部サービスの認証情報一般**(LLM・TTS・音声認識の API キー、および **Udemy のパスワードとセッションクッキー**)がリポジトリに平文で存在せず、ログ・エラーメッセージにも出力されない(検出 0 件)。環境変数または OS の資格情報ストア経由のみ。
- **How verified**: gitleaks、ログ出力の自動テスト、セッション保存先が `.gitignore` の対象であることのテスト、セキュリティレビュー。

### NFR-4: 段階的な再実行性
- **Criterion (measurable)**: 取り込み・クラスタリング・想起素材・台本・音声の各段階の中間成果物が永続化され、任意の段階から再実行したとき、それより前の段階の外部 API 呼び出し回数が 0 である。R-3 の再現性測定(キャッシュを迂回した再クラスタリング)はこの対象外とする。
- **How verified**: 途中段階を失敗させ、再実行時の外部 API 呼び出し回数を数える自動テスト。
- **R-3 の再現性測定の判定方法**: キャッシュを迂回した2回の再クラスタリングは実 API 呼び出しを2回要するため、NFR-6 のネットワーク遮断サンドボックスでは `command` の証拠にできない(スタブは決定的なので一致率が常に 100% になり、測る意味が消える)。この基準は **`artifact` 判定**とし、ホスト上での1回の実測ログをテストプランに記録する。`external` にすると D-003(evidence 待ちを発生させない)と衝突するため採らない。

### NFR-5: 開発基盤と CI
- **Criterion (measurable)**: (a) uv で依存が解決・同期できる、(b) ruff・mypy strict・pytest が全て通る、(c) pre-commit が全ファイルに対して通る、(d) **GitHub Actions のワークフロー定義がリポジトリに存在し、その `run` ステップのコマンド列と同一のものが品質ゲート上でローカルに green になる**(`actions/checkout` や `setup-uv` のようなアクションはローカルで走らないため、同一性の対象は `run` ステップに限る)、(e) `mkdocs build` が警告なく完了する。Python は 3.13 系。`PyProjectTemplate` から取り込む設定(pyproject.toml の ruff/mypy 設定、.pre-commit-config.yaml、mkdocs.yml、makefile)は本リポジトリ内に写し取り、外部パスを参照しない。
- **How verified**: 品質ゲートの各ステップの終了ステータス。テストプランに記録。
- **実 CI の green はこのサイクルの対象外**: push と pull request は人間承認のみの操作であり、ループは自力で CI の実行結果を取得できない。D-003 が external evidence の待ちを発生させないと決めているため、実 CI が green になることの確認は Out of scope とし、次サイクルの external evidence とする。

### NFR-6: 品質ゲートのネットワーク非依存
- **Criterion (measurable)**: 品質ゲートのコマンドステップが、ネットワーク接続なし(`.rein/config.yaml` の `quality` プロファイルは `network_profile: none`)で成功する。外部 API はテスト内で代替される。
- **How verified**: サンドボックス内での品質ゲート実行が green であること。
- **前提(2026-09-22 に実測済み、AR-15 は解消)**: 配布時の `rein-python` イメージは pytest と uv しか持たず、ruff・mypy・pre-commit・mkdocs をいずれも欠いていた。プロジェクト所有の `.rein/oci/quiz-sift/Containerfile` を作って ruff 0.15.16 / mypy 2.1.0 / mkdocs 1.6.1 を焼き込み、`quality` プロファイルのダイジェストを再ピンした。ネットワーク遮断下で5ステップすべてが green であることを確認済み。
- **`pre-commit` は品質ゲートに入れない**: フックを GitHub から clone するため `network_profile: none` では動作しない。同じ検査を ruff と mypy の直接実行としてゲートに置き、`pre-commit` はホストのコミット時と CI に任せる。

### NFR-7: 処理コストと所要時間の可視化
- **Criterion (measurable)**: 100〜200問の1回のフル処理について、経過時間・外部 API 呼び出し回数・推定コストの3項目が実行ごとに記録される。**推定コストはモデル別の単価と入出力トークン数を根拠として記録し、算出根拠がログから追跡できる**。上限値は初回実測後に設定する。
- **How verified**: 実行ログに3項目と算出根拠が存在することの自動テストと、初回実測値のテストプランへの記録。
