# ADR-002: LLM は Anthropic 1社、ports はタスク別メソッド

- **Status**: accepted
- **Date**: 2026-09-22
- **Decider**: human (finalized at the mandate)
- **Related requirements**: R-3, R-4, R-5, R-6, NFR-1, NFR-7

## Background / problem

D-008 が「クラウド API を差し替え可能なインタフェースの背後に置く」と決めている。
プロバイダの数と、インタフェースの粒度を決める必要がある。

## Options

### Option A: 1社 + 汎用 `complete()`
- Overview: `complete(prompt, response_schema) -> (text, usage)` の薄い Protocol。プロンプトは外出し。
- Cost: 単価表が1社分。
- Implementation effort: 最小。
- Pros / cons: YAGNI に最も忠実。ただし型が弱く、呼び出し側がプロンプトを組み立てる。

### Option B: 1社 + タスク別メソッド
- Overview: `classify_clusters()` / `summarize()` / `check_entailment()` のように用途ごとに切る。
- Cost: 同上。
- Non-functional: プロンプトが ports 側にあるので、プロバイダを差し替えるとプロンプトも一緒に動く。
- Implementation effort: 小。
- Pros / cons: 型が強く、各呼び出しの入出力が明示される。

### Option C: 2社実装して差し替えを検証
- Pros / cons: D-008 の主張を観測可能にするが、単価表も検証も2倍になり、仮説検証が目的の
  サイクル1では重い。

### Option D: SDK 無しで urllib 直叩き
- Pros / cons: 依存ゼロを守れるが、ADR-001 で依存を焼くと決めた以上その利点が消える。

## Decision

**Adopted**: Option B(1社 + タスク別メソッド)。プロバイダは Anthropic、モデルは `claude-opus-5`。

**Reason**: 用途が4つ(分類・要約・生成・含意判定)に限定されており、それぞれ入出力の形が違う。
タスク別メソッドにすると型で縛れ、`mypy strict` の下で呼び出し側の誤用が落ちる。

## Consequences / results

- `anthropic` Python SDK を依存に入れる(ADR-001 によりイメージに焼く)。
- モデルは `claude-opus-5`(入力 $5.00 / 出力 $25.00 per 1M)。`adaptive` thinking を既定とする。
- NFR-7 の単価表はこの1社分。`priced_at` に取得日を持たせる。
- プロバイダを変えるとプロンプトも `ports` 側で一緒に動く。**手書きフィクスチャ(D-044)は
  プロンプトに依存しないので、差し替えでフィクスチャが無効になることはない**。
- **What this requires of a person**: `ANTHROPIC_API_KEY` を環境変数に置くこと。
- **Reversibility**: 可逆。`adapters/llm_anthropic.py` の差し替えで済み、claim も受入基準も動かない。
